## 资源实测

### 在线存储

同一隔离 MySQL 实例读取 InnoDB 数据和索引统计，禁用元数据统计缓存后得到：

| 项目 | 字节 | 约值 |
|---|---:|---:|
| 旧完整结构 `pfm` | 2,961,784,832 | 2.76 GiB |
| 新运行库 `finance_rehearsal` | 68,468,736 | 65.30 MiB |
| 完整分片归档 | 850,730,453 | 811.32 MiB |
| 旧完整压缩备份 | 588,641,127 | 561.37 MiB |
| 新运行库压缩备份 | 6,359,470 | 6.06 MiB |

新运行库的数据和索引估算减少 **97.69%**；这不是总磁盘或内存下降比例。演练同时保留旧恢复库、核对库、额外压测克隆库、完整备份和归档，其总占用更高。归档包含逐记录来源和加密字段，不能与 SQL 压缩备份直接当作同一种文件比较。InnoDB 统计也不是物理文件空间回收证明。

### SQL 和 Linux API

同实例等价只读 SQL 的 P95（25 次）：月合计旧 **51.08 ms** / 新 **62.22 ms**；流水首页旧 **42.91 ms** / 新 **2.65 ms**；活动持仓旧 **1.67 ms** / 新 **1.55 ms**。新月合计查询仍有优化空间。

另外用本地旧版 Rust 发布包和按锁定依赖构建的新 Django/Gunicorn 镜像启动真实 Linux API。两者分别连接额外克隆库；均限制 1 CPU、1 GiB，并位于共享的 `pfm.slice`（1 CPU、1 GiB）内。数据库仍是本机 Windows MySQL，通过回环 SSH 隧道访问。依赖构建修复了 PyMySQL RSA 与原 cryptography 锁定版本冲突，干净镜像安装验证通过。

| 工作负载 | 旧 API 顺序 P95 | 新 API 顺序 P95 | 旧 4 并发 P95 | 新 4 并发 P95 |
|---|---:|---:|---:|---:|
| 流水首页 | 414.27 ms | 229.96 ms | 394.74 ms | **881.56 ms** |
| 持仓 | 1,094.20 ms | 125.54 ms | 177.22 ms | **272.52 ms** |
| 首页/家庭汇总 | 366.06 ms | 344.08 ms | 427.59 ms | **566.12 ms** |

每项预热 3 次、顺序 25 次、4 并发共 20 次。旧、新响应字段、汇总范围及缓存行为不同，例如旧首页响应约 976 KB，新家庭汇总约 597 B；此表不能证明完整功能等价。旧版二进制来自本地发布包，其 SHA 已记录，后续生产 SSH 连接重置，未能再次读取线上二进制摘要。

测试后 cgroup 记录旧 API 容器峰值约 **145.42 MiB**，新 API 约 **295.22 MiB**；新 API 的 CPU 限额节流也有发生。该峰值包含容器内测试客户端等开销，是本轮观测值，不能等同服务独占 RSS 或生产峰值。新系统本轮没有证明内存更低。原生接口中账户列表 38 次查询、标的列表 36 次查询、家庭汇总 23 次查询，应优先减少重复 ORM 查询。

**未完成的资源验收：**实际 2 GiB Linux 主机和 MySQL 8.0 的整体容量、浏览器页面 P95、长期负载、重型后台任务耗时和峰值。旧、新策略能力不等价，因此没有用不同任务的耗时冒充同负载对比。当前只能确认在线库明显变小，不能确认整机压力已降低。

临时 API 容器和 VM 隧道已关闭，任务启动的 Podman 虚拟机已恢复停止状态。额外压测克隆库保留在独立实例中，便于复现；生产未参加压力测试。
