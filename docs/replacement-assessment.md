# 旧系统替换评估

本轮以 `personal_financial_management_rust` 生产完整快照作为固定来源，目标为本机独立 `finance_rehearsal`。生产服务、生产数据库和本项目 `finance` 数据库没有切换。详细报告与业务数据仅保存在忽略的 `backups/migration-20261021/`，不提交个人财务明细。

## 已提供的兼容能力

- 完整备份、校验、隔离恢复、SELECT-only 来源账号、目标库名称及实例身份防护。
- 用户密码哈希、家庭成员及角色保留；家庭查询按有效成员限定，超级用户不自动取得全体家庭权限。
- 原始财务和配置事实在线保留；完整历史以校验分片归档，支持授权分页、证券及日期查询。凭据字段加密、接口脱敏。
- 流水按收入/支出分别转换，零金额作为资料记录保留，退款引用和标签保留；没有原资金账户的历史不会猜测归属。
- 现金账户沿用原期初余额及明确关联流水；证券和公积金保留快照余额基准，历史资金流不会再叠加到当前余额。
- 持仓保留原数量、成本、市值、收益及成本锚点；新买卖从快照边界继续计算，不补造建仓记录。可转债、黄金及万份收益类型可承载。
- 原债务和还款计划直接转换，不用当前利率重建历史；历史信用卡债务支持无原账单周期时的关联和部分还款。
- 家庭和历史资料页面：`/history`。接口位于 `/api/v1/history/*`、`/api/v1/household/summary`。

## 数据精简与资源边界

新 MySQL 保存小规模业务事实、兼容投影、来源映射与分片目录；大量行情、策略结果、冻结证据保存在压缩文件，不复制 321 张旧表到新运行库。近 90 天和更早历史均可通过同一归档接口查阅，但旧策略的计算能力仍属于待补齐功能。

这是存储位置和访问方式的变化，不是丢弃数据。资源报告必须分别计入新 MySQL、压缩归档、完整恢复备份和隔离旧库。演练时同时保留这些副本，不能用新 MySQL 的降幅声称总磁盘同幅下降。

Gunicorn 默认限制到最多 2 个 worker、每个 2 个线程；调度器单任务执行，防止多个计算任务同时争用 2 GiB 主机。生产部署仍需 Linux 上的容量和压力验收；本机 MySQL 8.4 的对比不代表生产 MySQL 8.0 的表现。

## 操作入口

1. `python scripts/migration_snapshot.py --ssh-config <已有授权配置> --host <来源主机> --run <唯一批次> --output backups/migration-20261021`
2. `python scripts/migration_instance.py start`，然后 `restore`。仅管理本轮实例，不清理原 MySQL 的 undo/redo 文件。
3. `python scripts/rehearsal_manage.py migrate --noinput`
4. `python scripts/rehearsal_manage.py legacy_migrate --source <私有 source.json> --output <同批次目录> --phase all`
5. 相同命令重复执行用于幂等检查；`--dry-run` 只检查来源和清单。分别提供 `ingest/project/verify` 阶段以支持中断续跑。
6. `python scripts/rehearsal_test.py -q`；前端执行 `pnpm typecheck`、`pnpm build`。

`rehearsal.env` 和 `source.json` 含私有连接信息；不得复制进公开文档。原 `backend/.env` 保持原值。

实际结果、资源测量边界和未完成的验收项见 [migration-verification.md](migration-verification.md)。
